# ChatDB SelfService - Requirements (Draft)

## 1. Цель
Система должна позволять аналитикам и разработчикам самостоятельно:
- настраивать подключения к базам данных;
- создавать триггеры на события в БД;
- получать уведомления по срабатыванию триггеров в выбранный канал.

## 2. Область решения
Продукт состоит из двух частей:
- **Чат-бот**: интерфейс управления подключениями, триггерами, пользователями и правами.
- **Канал уведомлений**: группа/чат/почтовый ящик, куда отправляются сообщения о событиях.

## 3. Термины и сущности
- **Пользователь (User)**: участник системы.
- **Роль (Role)**: базовый уровень прав (например, `Admin`, `DefaultUser`).
- **Группа (Group)**: объединение пользователей для назначения доступа.
- **Подключение (Connection)**: параметры подключения к конкретной БД.
- **Триггер (Trigger)**: правило, определяющее событие, при котором отправляется уведомление или запускается действие.
- **Канал уведомлений (Notification Channel)**: место доставки сообщений о событиях.

### 3.1 Связи между сущностями
- Один `Trigger` относится ровно к одному `Connection`.
- Один `Connection` может содержать один или более `Trigger`.

## 4. Регистрация и идентификация
### 4.1 Обязательные поля пользователя
- ФИО
- Рабочая почта

Набор обязательных полей может быть расширен конфигурацией проекта.

### 4.2 Начальная инициализация
- При старте системы существует ровно один **супер-администратор**.
- Супер-администратор может назначать роли и управлять пользователями.

## 5. Роли и права доступа
Минимально поддерживаются две роли:
- `Admin`
- `DefaultUser`

### 5.1 Права Admin
- Создавать, изменять и удалять подключения.
- Создавать, изменять и удалять триггеры.
- Создавать, изменять и удалять пользователей.
- Назначать роли и группы пользователям.
- Создавать и удалять группы.
- Настраивать видимость подключений и триггеров для групп пользователей.

### 5.2 Права DefaultUser
- Просматривать только доступные подключения и триггеры согласно настройкам видимости.
- Получать уведомления в доступных каналах (если разрешено политиками доступа).

## 6. Модель доступа (RBAC + группы)
### 6.1 Общий принцип
Доступ к объектам (`Connection`, `Trigger`) задается через:
- роль пользователя;
- членство в группах;
- правила видимости, заданные администратором.

### 6.2 Видимость по умолчанию
При создании каждого объекта (`Connection`, `Trigger`) администратор обязан указать группы, которым объект будет виден.

Обязательные правила:
- объект должен быть привязан минимум к одной группе;
- объект может быть привязан к более чем одной группе;
- пользователь видит объект, если состоит хотя бы в одной из групп, назначенных объекту.

## 7. Функциональные требования
### FR-1 Управление пользователями
- Система должна поддерживать регистрацию пользователя с обязательными полями.
- Система должна позволять администратору изменять данные пользователя.
- Система должна позволять администратору назначать роли и группы.
- Изменения прав доступа (роли, группы, видимость объектов) должны применяться только после согласования (апрува).
- До апрува изменение прав не вступает в силу.

### FR-2 Управление группами
- Администратор должен иметь возможность создавать и удалять группы.
- Администратор должен иметь возможность управлять составом групп.

### FR-3 Управление подключениями
- Администратор должен иметь возможность создавать, редактировать и удалять подключения.
- При создании подключения администратор обязан назначить минимум одну группу видимости.
- Одному подключению может быть назначено более одной группы видимости.

### FR-4 Управление триггерами
- Администратор должен иметь возможность создавать, редактировать и удалять триггеры.
- Триггер должен быть привязан ровно к одному подключению.
- При создании триггера администратор обязан назначить минимум одну группу видимости.
- Одному триггеру может быть назначено более одной группы видимости.
- Для триггера должен задаваться тип: `personal` или `public`.
- Понятие подписки применяется только к триггерам типа `personal`.
- При создании `personal`-триггера автоматически создается подписка автора триггера.
- Подписываться на `personal`-триггер могут только пользователи, имеющие доступ хотя бы к одной группе, назначенной этому триггеру.

### FR-5 Уведомления
- При срабатывании триггера типа `personal` система должна отправлять сообщение в чат-бот пользователю, который создал триггер.
- При наличии подписок у `personal`-триггера система должна отправлять сообщение всем подписанным пользователям.
- При срабатывании триггера типа `public` система должна отправлять сообщение в заранее определенный канал уведомлений.
- В интерфейсе должна быть доступна ручная повторная отправка уведомления по выбранному событию.
- Формат сообщения должен быть стандартизован и включать минимум:
  - время события;
  - источник (подключение/БД);
  - тип события;
  - ключевые данные события.

### FR-6 Доступ к каналу уведомлений без чат-бота
- Подключение пользователя к каналу уведомлений выполняется через стандартный функционал выбранной платформы (например, приглашение/добавление в канал).
- Управление доступом к каналу выполняется вручную администратором канала.

## 8. Нефункциональные требования
- **Безопасность**: хранение секретов подключений в защищенном виде (шифрование/secret store).
- **Аудит**: логирование административных действий (кто, что, когда изменил).
- **Надежность**: повторная отправка уведомлений при временных сбоях канала.
- **Расширяемость**: возможность добавлять новые типы триггеров и каналы уведомлений.
- **Кросс-СУБД поддержка**: система должна поддерживать распространенные СУБД (минимум PostgreSQL, MySQL/MariaDB, MS SQL Server, Oracle, SQLite).
- **Поддерживаемость**: бизнес-логика в приложении, БД как слой хранения и запросов.

## 9. Ограничения и архитектурные принципы
- Доменная логика должна быть реализована в ООП-слое приложения.
- База данных должна использоваться для хранения конфигурации, состояний и журналов.
- База данных инициализации по умолчанию: SQLite.
- Должен использоваться отдельный конфигурационный файл инициализации, в котором хранятся:
  - токен приложения/бота;
  - имя пользователя первоначального супер-администратора.
- Рекомендуемый формат конфигурационного файла: `config.yaml`.
- Обязательные поля конфигурации:
  - `bot_token` - токен приложения/бота;
  - `initial_superuser_name` - имя пользователя первоначального супер-администратора.
- Не допускается перенос критической доменной логики исключительно в SQL-скрипты/триггеры БД без слоя приложения.

## 10. MVP (первая версия)
В первую поставку включить:
- Регистрация пользователя.
- Роли `Admin` и `DefaultUser`.
- CRUD для подключений.
- CRUD для триггеров.
- Настройка видимости подключений и триггеров по группам.
- Отправка уведомлений в один выбранный канал (по умолчанию в MVP - Telegram).
- Ручная повторная отправка уведомлений из интерфейса.
- Согласование (апрув) изменений прав доступа перед применением.
- Полноценная поддержка БД в MVP: SQLite (по умолчанию) и PostgreSQL.
- Остальные распространенные СУБД подключаются через расширяемый драйверный слой на следующем этапе.
- Базовый аудит административных действий.

## 11. Критерии приемки MVP
- Администратор может создать подключение и триггер.
- Пользователь `DefaultUser` видит только разрешенные объекты.
- При тестовом событии триггер отправляет уведомление в канал.
- Администратор может вручную повторно отправить уведомление по выбранному событию.
- Изменение прав доступа не применяется без апрува и применяется после успешного согласования.
- В журнале аудита фиксируются изменения прав и конфигураций.

## 12. Вопросы на уточнение
- Канал уведомлений по умолчанию для MVP: Telegram.
- Многоарендность (несколько независимых контуров/проектов) в MVP и текущей версии не требуется.
- Триггер привязывается только к одному подключению.
- Ручная повторная отправка уведомлений из интерфейса требуется.
- Согласование (апрув) изменений прав доступа требуется.
